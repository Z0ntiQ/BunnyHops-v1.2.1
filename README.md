# Bunny Hops v1.2.1 — REST-клиент, API-прокси, мок-сервер и MCP-мост

**Версия: 1.2.1 · Билд: `b20261119-r1` (сборка от 2026-11-19, macOS arm64 + Windows x86_64)** —
`CFBundleVersion` внутри `Bunny Hops.app/Contents/Info.plist`.


- **Мок-редактор: пустой экран и удаление**: на пустом экране редактора моков —
  зелёная кнопка «Добавить правило», открывает пустой черновик правила. В свёрнутой
  строке правила и варианта ответа — крестик удаления с модалкой подтверждения
  (Enter — удалить, Esc — отмена).
- **Windows-сборка в релизе**: оконное приложение `bunny-hops-desktop.exe`
  и headless-сервер `bunny-hops-server.exe` (x86_64, без установщика, без прав
  администратора). Релиз с двумя платформами из одного исходного кода.

Локальный инструмент для ручной и автоматизированной работы с HTTP: интерфейс REST-клиента,
прокси против CORS, генератор ответов вместо внешней системы (мок), журнал всех действий.
Всё работает без установки Node, без прав администратора, данные не уходят наружу.

## Запуск

Оконное приложение: открыть `Bunny Hops.app`. Сервер стартует на случайном свободном порту,
полный адрес — в заголовке окна. Закрытие окна останавливает процесс.

Headless-сервер:

```bash
cd server
PORT=3000 ./bunny-hops-server        # PORT обязателен для строгого порта; без него — авто-порт
# UI: http://127.0.0.1:3000/
```

Windows headless (PowerShell):

```powershell
cd win
$env:PORT="3000"; .\bunny-hops-server.exe
# UI: http://127.0.0.1:3000/
```

Проверка живости: `curl -s http://127.0.0.1:3000/api/status` → JSON с версией и аптаймом.

## Инструменты: что можно и что нельзя

### 1. REST-клиент (веб-интерфейс)
Модель клиента: вкладка-профиль с сохранёнными настройками, запрос уходит через локальный прокси — CORS не мешает.

Можно:
- Все методы REST: GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS.
- Params — синхронизированы с адресной строкой в обе стороны.
- Headers — произвольные заголовки запроса.
- Body — JSON-редактор с индикатором валидности (для методов с телом).
- Vars — переменные `{{name}}`, подставляются в URL, заголовки и тело.
- Scenario — цепочка шагов-запросов: ответ шага N разбирается по JSONPath (`$.data.token`),
  захваченные значения подставляются в шаг N+1; по каждому шагу ✔/✖. Хранится локально.
- Ответ — стриминг по мере поступления, живой поиск по экрану, превью картинок,
  зум A−/A+ только для редактора тела и просмотра ответа.
- Профили — несколько именованных рабочих сессий, состояние сохраняется в браузере.
- Пустые KV-строки показывают живой пример по смыслу вкладки (URL с параметром,
  заголовок, переменная) — пример набирается один раз и не мешает вводу.

Нельзя:
- Помощника авторизации (Basic/Bearer/OAuth) нет — заголовки авторизации ставятся вручную в Headers.
- Редактора multipart/form нет — тело передаётся как есть (raw).
- UI показывает первые 200 000 символов ответа; тема интерфейса только тёмная.

### 2. Прокси `/proxy` — единая точка HTTP
Стриминговый прокси против CORS. Тот же путь, что у UI; доступен агенту через curl.

Можно:
- Любой метод, любое тело (кроме GET/HEAD — тело игнорируется), query внутри `?url=`.
- Заголовки цели — JSON в заголовке запроса `X-Proxy-Headers`.
- Ответ цели 1:1: реальный статус, заголовки (кроме hop-by-hop), тело стримом;
  после редиректов — `X-Proxy-Final-Url`. Декодирование gzip/brotli/deflate.
- Прозрачные классы ошибок: DNS, connection-refused, timeout — как в браузере.

Нельзя:
- Тело запроса больше 32 МиБ → 413 JSON до обращения к цели.
- Больше 10 редиректов; таймауты: 10 с на соединение, 120 с всего.
- Отключить перерисовку больших ответов: UI обрезает показ, API отдаёт полностью.

### 3. Мок-режим (BunnyProx) — подмена внешней системы
Локальный HTTP-сервер вместо реальной системы (например 1С): профиль слушает свой порт
и отвечает по правилам «путь + метод → JSON-вариант».

Можно:
- Несколько профилей на разных портах, старт/стоп на ходу.
- **Мок слушает 0.0.0.0** — корпоративный стенд может вызвать его по LAN-адресу машины
  как настоящую внешнюю систему.
- Несколько вариантов ответа на правило (ротация), шаблоны JSON с токенами-рандомайзерами:
  `{{guid}} {{int:}} {{float:}} {{bool}} {{date:±N}} {{datetime:}} {{string:}} {{pick:}}
  {{email}} {{phone}} {{hex:}} {{inn}} {{snils}} {{name}}` — свежие значения в каждом ответе.
- Preview до запуска, журнал traffic (что приходило и чем отвечено) — панель Traffic
  доступна рядом с Logs, агрегация по вызовам.
- Профили хранятся в `~/.bunny_hops/mock/<имя>.json`.

Нельзя:
- Только HTTP без TLS; только JSON-ответы; правило матчится по пути и методу
  (сложной логики «ответ зависит от тела запроса» нет).
- Нет правила → 404 (это ожидаемое поведение, не ошибка сервера).

### 4. Журнал действий
Через единый логер проходят все действия приложения: вкладки, CRUD моков, запросы прокси,
заметки UI, `/screenshot`. Просмотр — панель «Logs» в интерфейсе или `GET /api/action-log` (cap 500, свежие сверху).

Нельзя: журнал в памяти процесса, после перезапуска пустой. Долгие цепочки прогонов —
забирайте JSON из API и сохраняйте сами.

### 5. Кадр окна: `/api/eyes` и `/screenshot`
- `/api/eyes` (оконная версия) — снимает текущее окно приложения и отдаёт PNG.
  Чистая функция: состояние окна → кадр, адресов глаз у эндпоинта нет.
- `/screenshot` (публичный, без гейта debug-API) — склейка кадров окна приложения
  (панель запроса + ответ) через CDP. В headless без окна — честный `502` с JSON-ошибкой.

### 6. Control API — автоматизация без UI
Выполнение запросов, профили-базы, история — всё через HTTP из скриптов.
Полный список с контрактами: `docs/API.md`.

### 7. JSON-RPC мост `/rpc` и MCP-сервер (новое в 1.1.0)
Единая POST-точка JSON-RPC 2.0 для внешнего клиента: методы debug-поверхности
(state, dispatch, elements, wait-предикаты) под Bearer-токеном.
Токен — в lock-файле `~/.bunny_hops/rpc.json` (права 0600), порт — там же.
Поверх моста работает MCP-сервер broop: агент видит приложение как набор
MCP-инструментов (`inspect_ui_tree`, `ui_click_by_id`, `execute_business_action`, …).

Нельзя: без Bearer-токена `/rpc` отвечает `-32600 Bearer token required`;
мост под тем же гейтом debug-API, что и `/debug/*`.

| Где | Что |
|---|---|
| `~/.bunny_hops/` | Профили control-плоскости (`profiles.json`), тема, конфиги моков, `rpc.json` (токен+порт, 0600) |

## Границы релиза v1.2.1

- Бинарники собраны под macOS (arm64) и Windows (x86_64). Linux — на Linux
  (см. `desktop/BUILD-WINDOWS.md` в исходниках).
- Секретов в конфигурации нет; ключи для корпоративных API — только в Headers запроса.
  Токен `/rpc` — локальный, в lock-файле.
- Все сетевые серверы слушают 127.0.0.1, кроме моков: мок-профиль — 0.0.0.0
  (доступен из LAN по явному назначению «внешняя система»).
- Смоук этого релиза проверен на headless-бинарах macOS и Windows (`/api/status` → v1.2.1, гейты,
  `/screenshot` жив). Оконная сборка — тот же код, что работает на машине сборки.
